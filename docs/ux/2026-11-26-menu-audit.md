# Workplot 메뉴 사용성 점검 · 2026-11-26

한국시간 오전 8시 49분부터 정오까지 4310에서 점검했다. 기본 화면은 1440×850과 390×850이며, 필요한 항목은 320×690과 844×390 등에서도 재현했다. 아래 우선순위는 업무를 방해하는 정도에 대한 판단이다. 참가자의 선호도나 행동 시간을 측정한 수치는 아니다.

## 수정 후 확인 · 11월 26일 저녁

Runs 13건, Library 10건, Editor 12건, 공통 3건을 수정했다. 아래 원래 목록의 01–38번에 대응하는 브라우저 점검이 모두 통과했다. 4310에서 제공하는 화면과 기존 실행 기록을 사용했다. 조회 실패, 요청 전송 실패, AI 추천 응답은 브라우저에서 재현했다. 실제 승인이나 새 Codex 실행은 수행하지 않았다.

- Runs의 모바일 승인 카드에서 첫 번째와 세 번째 행동 사이 거리가 980px에서 약 317px로 줄었다. 실행 상세에서는 문서를 생성하기 전에 멈춘 경우에도 마지막으로 확인된 단계와 로그를 찾을 수 있다.
- Library에서는 예약 자료의 입력 방식을 바꿨다가 돌아와도 적은 내용이 유지된다. [수정 전](2026-11-26-evidence/library-schedule-after.png) · [수정 후](2026-11-26-evidence/fixed-schedule-draft.png)
- Editor에서는 844×390 화면에서도 와이어 위 결과 문서를 열 수 있다. 문서를 닫으면 해당 버튼으로 키보드 포커스가 돌아온다. [수정 전](2026-11-26-evidence/editor-landscape-wire.png) · [수정 후](2026-11-26-evidence/fixed-landscape-wire.png)

### 확인한 정상 동작

- 영어 버튼 점검에서 사용자 콘텐츠를 구분했다. 대표 실행 상세의 “검증한 변경 커밋”은 결과 파일을 여는 버튼에 표시된 단계 제목이고, Library의 “내 워크플로 화면 개선 루프” 등 11개는 저장된 흐름 이름이었다. 이 이름들은 원문 유지 대상으로 분류했다. 세 상세 화면의 짧은 가시 문구(35자 미만) 표본이며, 서비스 전체 버튼의 영어화를 입증하는 검사는 아니다.

- 흐름 설계 개선 v11의 첫 노드 지침은 496자였다. 390px에서 입력란의 표시 높이는 136px, 내용 높이는 448px였다. 1440px에서는 각각 114px와 231px였다. 양쪽 입력란에 세로 크기 조절 스타일이 있었고, 390px Mac Chromium에서 Command+↓를 누르면 커서가 496번째 문자로, 내부 스크롤이 312px로 이동했다. 1440px에서 마우스로 입력란 우측 하단을 95px 아래로 끌자 바깥 높이가 115.5px에서 210px로 늘었다. Role and instructions를 접었다 펴도 210px가 유지됐다. 터치 기기의 크기 조절 조작과 실제 가독성은 이 측정으로 판단하지 않는다. 높이를 850px로 고정해 첫 지침 입력란의 시작 위치도 비교했다. 화면 너비 320·390·768·1024·1440px에서 각각 상단으로부터 784·740·692·448·354px였다. 320px에서는 입력란의 138px 중 첫 화면에 최대 66px만 들어오는 배치다. 첫 화면에서 읽히는 분량에 대한 참가자 가설을 검증할 때 이 너비를 포함한다.

- 새 흐름의 첫 Prompt를 두 번 바꾼 뒤 상단 Undo를 두 번 눌렀다. 첫 클릭은 직전 문장과 Unsaved changes 상태를, 두 번째는 빈 원문과 초기 Unsaved 상태를 복원했다. 되돌릴 내역이 모두 사라지자 Undo도 비활성화됐다.

### 세 메뉴의 활성 버튼 글자 대비 대조

브라우저의 색상 선호를 light와 dark로 바꿔 각 메뉴의 기본 화면을 열었다. 렌더링된 활성 텍스트 버튼 중 자체 배경이 불투명 단색이고 배경 이미지와 요소 투명도가 없는 경우에 대해, 글자와 배경의 계산된 RGB 상대 휘도 비율을 구했다.

|---|---|---|
| Runs | Start with a goal · 8.77:1 | Next · 5.33:1 |

추가로 Library에서 선택된 ‘Workplot 기능 연구·확장’ 행의 투명 배경 버튼 두 개를 측정했다. 즐겨찾기 아이콘 / 행 메뉴 아이콘 / 키보드 초점 테두리와 행 배경의 대비는 라이트에서 10.52:1 / 5.39:1 / 6.24:1, 다크에서 9.22:1 / 5.36:1 / 8.13:1였다. 두 버튼 모두 초점 테두리 폭 3px·간격 3px였다. 이 결과는 선택된 행에서 두 아이콘의 표현만 다루며, 아이콘 의미가 설명되는지는 행 아이콘 동작 설명 항목에서 별도로 다룬다.

Editor에서 서버 구현과 같은 버전 충돌 응답(409, stale_version)을 브라우저에서 모의했다. 이때는 다른 변경이 먼저 저장됐다는 원인과 작업 목록에서 최신 버전을 다시 열라는 안내가 나타났고, 입력 원문과 Unsaved changes 상태도 유지됐다. 알림 자체에는 최신 버전을 여는 버튼이 없었다. 이 사례는 실제 동시 저장 시험이 아니며, 연결 실패용 문구를 적용할 때 이미 구체적으로 표시되는 충돌 안내를 유지할 대조 조건이다.

Library의 예약 저장에서도 동일하게 재현했다. 고정 자료를 작성하고 예약 저장 요청만 차단하자 폼과 원문이 유지되고 Save schedule을 다시 누를 수 있었지만, 오류 알림은 Failed to fetch였다. 세 메뉴에서 요청 원문 보존과 재시도가 가능했던 점을 유지하며, 안내는 각각 다음 회차 요청·흐름 저장·예약 저장 중 실패한 동작을 밝혀야 한다. 한 가지 공통 과제로 집계했다.

Editor의 기존 흐름 저장에서도 같은 안내가 나오는지 대조했다. 수정된 Prompt의 저장 요청만 브라우저에서 차단하자 Failed to fetch가 알림으로 표시됐다. 원문과 Unsaved changes 표시는 유지됐고 Save도 다시 누를 수 있었다. 읽기 요청은 정상 연결되어 있었으므로 하단의 연결 상태만으로 특정 저장의 성공을 판단할 수 없다. 오류 안내에는 실패한 동작과 실제 저장 여부를 구분해 표시한다.

| 우선순위 | 화면과 행동 | 기대와 관찰 | 사용자 영향과 개선안 | 합격 기준 |
|---|---|---|---|---|
| 중간 | <a id="ux-32"></a>다음 회차 요청에 문장을 쓰고 Submit request를 누른다. 테스트 브라우저에서 전송을 차단해 연결 실패를 재현했다. | 원문이 남고 제출 버튼도 다시 활성화됐다. 화면에 추가된 안내와 접근성 알림은 모두 “Failed to fetch”였다. | 사용자는 요청이 접수됐는지, 직접 재시도해야 하는지 알기 어렵다. 접수 확인에 실패했다는 점과 연결 복구 후 할 행동을 요청란 옆에 표시한다. | 같은 실패에서 원문이 유지되고, 요청 접수 상태와 재시도 방법을 알림으로 읽을 수 있다. |

요청을 테스트 브라우저에서 보류해 응답 대기 상태도 확인했다. 버튼은 Submitting…으로 바뀌고 입력란과 제출 버튼이 모두 비활성화됐다. 보류한 요청을 연결 실패로 끝내자 원문이 유지되고 제출 버튼이 다시 활성화됐다. 안내 개선 후에도 이 대기·복구 동작은 유지한다.

### Library · 처음 방문해 새 흐름 만들기

새 브라우저의 390px Library에서 탐색 링크는 Runs·Library·Editor였고, 검색과 기존 흐름 목록이 보였다. 새 흐름을 만든다는 이름의 버튼은 확인되지 않았다. Editor 링크를 누르자 ‘새 작업 흐름’이 열렸다. 이 경로로 생성 화면에 도달할 수 있다는 점은 확인했다. 처음 방문하는 사람이 Editor라는 이름만 보고 생성 위치를 찾는지는 참가자 관찰이 필요한 가설로 남긴다.

Create workflow from goal을 열면 목표가 비어 있을 때 Generate design이 비활성이다. “주간 작업의 근거를 검토”를 입력한 뒤 Escape로 닫고 다시 열자 목표는 비어 있었다. 의도적으로 생성을 취소한 경우와 잠시 기존 흐름을 참고하려는 경우의 기대가 다를 수 있어, 이 사례를 입력 손실 확정 건수에 더하지 않았다. AI 생성이나 저장은 실행하지 않았다.

새 브라우저에서 직접 연 Editor의 첫 단계는 AI 작업 한 개였다. 390×850에서 Role and instructions가 펼쳐져 있고 Prompt는 빈 값이었다. 입력란에는 자료·작업·결과를 적으라는 예시가 표시됐다. 임시 지침을 입력하자 첫 노드의 역할 미리보기에도 같은 문장이 표시됐다. 새 초안에서 예전 매장 과제가 기본 지침으로 채워지는 현상은 이 경로에서 재현되지 않았다.

### Editor · 직접 편집한 프롬프트의 보존 범위

저장된 v11 흐름에서 node-research-plan의 지침 본문에 임시 문구를 추가한 채 우측 결과를 열었다. 390px·1440px 모두 자료 조회가 끝나자 모달 상단에는 ‘문서를 생성한 실행 · v11’, 최신 199회차와 이전 198·197회차의 시각이 표시됐다. 결과를 닫은 뒤 임시 문구도 유지됐다. 따라서 지침 편집이 이전 회차 결과를 즉시 다시 생성한다는 문제는 이 경로에서 재현되지 않았다. 다만 이 표시만으로 처음 보는 사람이 저장 전 편집과 결과의 관계를 이해하는지는 참가자 관찰 대상으로 남긴다.

390px와 1440px의 새 브라우저 세션에서 저장된 흐름의 Prompt 끝에 임시 문구를 입력했다. Library로 이동한 뒤 브라우저 뒤로가기로 같은 흐름을 열었을 때와 그 자리에서 새로고침했을 때 모두 문구가 남았다. 흐름 저장 버튼은 누르지 않았다. 초안 손실 개선은 노드별 Refine 요청 입력란에서 재현되며, 같은 탭에서 직접 편집한 Prompt 본문은 복원된다. 두 필드를 구분해 회귀 검사를 구성할 수 있다.

같은 브라우저의 새 탭에 편집 주소를 복사해 여는 경우도 대조했다. 원래 탭에서는 임시 문구와 Unsaved changes가 보였고, 새 탭에서는 수정 전 본문이 정확히 일치했으며 Unsaved changes가 표시되지 않았다. 따라서 직접 편집 초안의 새로고침 복원과 주소 공유로 열리는 저장 버전은 별도로 검증할 수 있다.

### Runs · 완료 버전 재사용의 준비 단계

활성 실행이 있는 실제 목록에서 완료 실행 94c0cf81의 상세와 문서 비교 모두 Reuse this version이 비활성화됐다. 버튼과 바로 바깥 요소의 title, 버튼의 aria-describedby는 비어 있었고 인접한 안내도 없었다. 대조용 브라우저에서만 실행 목록 조회를 빈 목록으로 응답시켰더니 같은 버튼으로 ‘흐름 설계 개선 · v11’의 ‘새 자료로 실행’ 창이 열렸다. 실제 작업 생성 요청은 0건이었다. 기존 ‘실행 가능한 경로 노출’ 과제의 추가 사례다. 활동 중인 실행 때문에 최종 시작만 막힐 때, 사용자가 자료를 준비할 수 있는지와 언제 시작할 수 있는지를 구분해 안내하는 기준에 포함한다.

### Runs · 처음 작성한 업무 목표 복원

390px·1440px에서 Start with a goal을 열면 ‘어떤 결과를 만들고 언제 직접 확인하고 싶으세요?’라는 입력란에 즉시 키보드 초점이 잡혔다. 배포 요약 초안과 직접 검토가 포함된 목표를 쓰자 Find workflow가 활성화됐다. 이를 제출하기 전에 Escape를 누르면 창이 닫혔고 시작 버튼으로 초점이 돌아가지 않았다. 다시 열었을 때 작성했던 목표는 두 폭 모두 비어 있었다. 미전송 초안 보존 과제에 이 경로를 포함한다. 같은 탭에서 창을 실수로 닫았다 다시 열 때 목표를 복원하고, 의도적으로 지우는 동작을 구분하는 것이 검증 기준이다. AI 실행이나 새 흐름 생성은 수행하지 않았다.

목표 검색 요청만 브라우저에서 가로채 통신 단절과 서버 일시 이용 불가(503)를 각각 재현했다. 두 조건 모두 원문이 유지되고 Find workflow를 다시 누르면 검색 요청이 한 번 더 발생했다. 단절 시에는 “Failed to fetch”, 503에서는 “로컬 서버 요청을 완료할 수 없습니다.”가 표시됐다. 기존 전송 오류 안내 개선 과제에 이 경로를 포함한다. 검색이 끝나지 않았고 작성한 목표는 남아 있으므로 연결 복구 후 같은 버튼으로 재시도할 수 있다고 알려 주면 된다. 실제 AI 호출은 발생하지 않았다.

### Editor · 단계별 도구와 Git 권한

390px의 v11 단계 속성에서 다섯 단계를 각각 선택했다. AI 검토와 다음 회차 준비에는 ‘Git 개발 실행 시 · 읽기 전용’, 개발 및 Git 반영에는 ‘파일 수정 허용’이 표시됐다. 라우터의 도구 패널에는 담당 도구·작업 스킬·사용 도구가 있고 Git 권한 입력은 없었다. 사용자 승인 단계에는 Tools and permissions 패널이 없었다. 첫 AI 검토 단계에서 Allow file edits를 누르면 선택값과 적용 안내가 함께 쓰기로 바뀌고, Undo 한 번으로 원래 자동 설정으로 돌아왔다. 이 점검은 편집 화면의 표현과 로컬 초안만 다루며 실제 파일 쓰기 권한 집행을 시험한 것은 아니다.

AI 검토 단계의 담당 도구 선택기는 Codex와 미지정을 선택할 수 있고, Claude Code는 ‘실행 미연결’로 표시되며 실제 선택지도 비활성화돼 있었다. 미지정을 선택하자 초안 선택값이 변경되고 Undo가 활성화됐다. 공통 Agent tools의 ‘설치 확인’과 해당 노드에 담당 도구로 연결 가능한지는 화면에서 서로 다른 상태로 표시됐다.

Library 예약 양식의 저장·취소는 `Save schedule`, `Cancel`로 표시됐다. Editor의 `GPT settings`를 누르면 모델 선택에 키보드 초점이 이동했다. 연결한 폴더와 반복 단계의 동작도 `Change folder`, `Disconnect`, `View loop step`으로 표시됐다. 영어 표기 과제에서 이 다섯 버튼은 제외했다.

Editor 키보드 복귀 추가 검증([문서 닫기](#ux-05)). 390×850과 1440×850 모두 단계 속성에서 199회차 파일 버튼에 초점을 두고 Enter로 연 뒤 Escape로 닫았다. 초점은 본문으로 이동했고 이어서 Tab을 두 번 누르자 두 화면 모두 `Runs → Library` 순서로 이동했다. 키보드 사용자는 읽던 단계에서 계속하려면 전체 탐색을 다시 거쳐야 한다. 수정 후에는 Escape 직후 같은 파일 버튼에 초점이 있고 다음 Tab이 해당 버튼 다음의 조작으로 이동하는지 확인한다.

Editor에서 아이콘만 보이는 와이어 도구를 키보드로 점검했다. 1440×850에서 이름은 `Zoom In`, `Zoom Out`, `Fit View`로 읽혔다. Enter를 누르면 배율이 차례로 약 63% → 75% → 63% → 67%로 바뀌었고, 세 번 모두 누른 버튼에 초점이 유지됐다. 아이콘·영어 동작명·키보드 조작을 함께 제공하는 기존 사례로 확인했다.

320×690 교차 점검. Runs 목록, Library의 기능 연구·확장 상세, Editor의 흐름 설계 개선에서 문서 전체의 실제 폭이 각각 320px였다. 페이지 전체 가로 넘침은 세 경로 모두 0px다. 이는 표나 와이어처럼 자체적으로 이동하는 영역의 조작 편의성과는 별개다.
