# Workplot 서비스 검토와 Git 개발 계획

2026-11-22 · 로컬 서비스와 현재 작업 트리를 기준으로 한 설계안

**첫 출시의 성공 조건은 사용자가 실행 전에 어느 서비스의 소스를 바꿀지 알 수 있고, 실행 후에는 어느 작업과 검사가 그 변경을 만들었는지 추적할 수 있는 것이다.** 독립 과제 두 개의 병렬 실행을 첫 대상으로 삼는다. 문서 작성, 여행 계획, 승인처럼 소스 수정이 없는 업무는 Git 등록 없이 실행한다.

### 실측과 한계

- 로컬 Chromium에서 실행 현황, 내 워크플로 상세, 와이어 설계, 완료 실행 상세를 열었다. 완료 문서의 렌더링된 본문을 확인했고 이 경로에서 페이지 오류는 0건이었다.
- 운영용 로컬 SQLite에서 흐름 10개, 저장 버전 28개, 실행 188건을 조회했다. 마스터 실행은 이 DB에 0건이었다. 보관된 별도 QA의 마스터 통합 세 건은 검증 통과였고, 대상은 격리된 UI 작업본이다.
- 현재 작업본의 자동 테스트 20개 파일, 73개 검사가 통과했다. 전체 포맷 검사는 기존 파일 세 개에서 실패했다. 직전 통합 QA 기록에는 첫 사용 경로·장애 복구·브라우저 검사가 통과로 남아 있다. 이번 검토에서 실제 Codex 전체 QA와 실사용자 평가는 반복하지 않았다.
- 포맷 실패 파일은 `docs/phase-1/feature-priorities.md`, `examples/next-session-preparation.json`, `examples/workplot-feature-research.json`이다. 이 결과도 첫 기준선의 검사 판정에 포함한다.

## 먼저 풀어야 할 문제

1. **실행 중인 앱과 Git 기준선의 차이.** 점검 당시 로컬 `main`은 `63009bc8f707e5463c4ad1e401833a6e86d2d60a`였고 추적 파일 34개가 수정됐으며 미추적 파일은 92개였다. 원격 설정은 `Raunplaymore/Workplot`이다. 마지막으로 받아 둔 `origin/main`과 로컬 HEAD는 같았다. 원격 최신 상태는 별도 확인 대상이다. 지금 HEAD만 복제하면 현재 실행기와 UI의 상당 부분이 빠진다.
2. **경로와 실제 수정 권한.** 기존 실행기는 첨부 사본을 인계하지만 작업 폴더는 경로로 지정한다. 전용 UI 개발 노드가 없는 흐름에서는 일반 Codex 작업 단계에도 그 폴더의 쓰기 권한이 전달될 수 있다. 새 Git 실행 모드에서는 계획·검토는 읽기, 구현은 지정된 worktree 쓰기로 실행기가 집행한다. 검토 지침 문구에만 맡기면 노드 역할과 실제 권한이 어긋난다.
3. **지금의 통합 단위.** 마스터는 Workplot 웹 소스 사본에서 파일별 변경을 합친다. 같은 파일의 서로 다른 내용은 파일 단위 충돌로 처리하고, 파일 추가·삭제는 실패 처리한다. Git 커밋과 대상 브랜치 반영 기록은 이 경로에 없다.
4. **AI 세션과 작업의 수명이 다르다.** 실행기는 일시적 Codex 호출을 사용하고 실행 레코드에 세션 ID를 기록한다. 여러 노드·재시도의 전체 호출 이력을 한 세션 ID로 표현하기 어렵다. 사용자가 이어가는 단위는 작업 ID로 삼고 호출은 그 아래 누적한다.

SQLite가 승인·실행·인계 이력을 보관하고 Git이 소스 내용과 계보를 보관한다. 기존 실행 레코드는 Git 필드를 선택 사항으로 읽는다. 과거 실행을 현재 브랜치에 소급해 귀속하지 않는다.

## 사용자가 보게 될 화면

- **내 워크플로 / 실행 준비** — 소스 수정 모드에서 `Workplot › Raunplaymore/Workplot › apps/web · main`을 한 줄로 확인한다. 상세에서 기준 SHA, 로컬 복제본, 참조 자료와 쓰기 범위를 본다. 저장소가 여러 개 매칭되거나 대상이 이동했으면 실행 전에 다시 고른다. 라이브러리·설계 화면의 실행 버튼 모두 같은 준비 화면을 사용한다.
- **마스터 와이어** — A와 B에는 각각 개발·검증 상태를, 합류점에는 통합 검사와 반영 상태를 표시한다. B에서 막히면 B를 눌러 충돌 파일이나 실패한 검사를 열고 A의 검증 결과도 확인할 수 있다.
- **실행 상세** — 개요에는 서비스·작업·현재 상태를, 상세에는 회차별 AI 호출·문서·diff·검증한 커밋을 표시한다. 새로고침과 주소 공유로 같은 실행·후보를 다시 연다. 사용자에게 일상적으로 SHA를 기억하게 할 필요가 없다.
- **예약·스킬·자동 위임** — 소스 수정 업무는 등록된 대상을 명시적으로 바인딩한다. 대상이 사라지거나 달라지면 원인을 표시하고 대기한다. 다음 세션 자동승인의 시간·횟수 한도는 개발을 이어갈 권한이며 기준 브랜치 반영 권한은 독립적으로 설정한다.

## Git 실행과 장애 복구

1. **기준선 고정.** 파일럿은 검토한 커밋에서 시작한다. 현재 Workplot은 변경된 추적 파일·미추적 파일·제외 경로 목록을 먼저 보여주고, 사용자가 선택한 소스만 임시 인덱스와 전용 로컬 ref로 기준선 후보를 만든다. 기존 인덱스와 원래 체크아웃을 보존한다. 자격 증명, 실행 DB, 첨부, 빌드 산출물을 제외하고 깨끗한 worktree에서 설치·빌드·대표 동작을 확인한 SHA를 채택한다. 기존 포맷 실패는 해소하거나 알려진 실패로 따로 기록한다.
2. **격리와 쓰기 범위.** 하위 작업마다 Workplot이 관리하는 저장소에 전용 브랜치와 worktree를 만든다. AI는 선택한 작업 파일을 수정하고 서버가 경로와 diff를 검사해 체크포인트 커밋을 만든다. 공용 Git 메타데이터·다른 worktree·원본 체크아웃의 쓰기는 실행 경계에서 막는다. 서비스 경로 밖의 변경, 공유 패키지, 심볼릭 링크, 서브모듈은 첫 버전에서 명시적 범위 확인 대상으로 둔다. 검사 프로세스와 데이터·포트도 작업별로 분리한다.
3. **통합.** 자식 결과를 고정 SHA로 큐에 넣고 대상별로 한 건씩 처리한다. 임시 통합 worktree에서 공통 조상을 기준으로 병합한 후 타입·빌드·계약·관련 화면 검사를 실행한다. 텍스트 충돌은 파일과 작업을 표시하고, 깨끗하게 병합됐어도 검사가 실패하면 실패 로그와 마지막 통과 후보를 남긴다. A 통과 뒤 B가 실패하면 B에서 고친 뒤 최신 후보 위에서 다시 검사한다.
4. **반영.** 첫 버전의 납품물은 로컬에서 검증한 통합 후보 브랜치다. 사용자 반영 승인은 정확한 후보 SHA와 예상 대상 SHA의 쌍에 묶는다. 대상이 움직이면 새 후보를 만들고 재검사한다. 체크아웃 중인 사용자 브랜치를 뒤에서 ref만 바꾸면 인덱스·파일과 어긋날 수 있다. 사용 중이거나 변경 중인 체크아웃은 후보로 전달하고, 원격 push·PR·배포는 후속 이정표에서 각각 별도 동작으로 설계한다.
5. **중단·재개.** 작업 공간 생성·커밋·병합마다 작업 키와 예정 ref를 먼저 기록하고, Git 수행 후 실제 SHA를 확인해 SQLite에 결과를 확정한다. 서버가 중간에 죽으면 ref·worktree·미커밋 diff를 대조한 뒤 미완료 연산만 이어간다. 중단·한도 대기 시 개발 중인 파일을 보존한다. 사용자 수정이 끼어든 작업 공간은 복구 대기로 보낸다. 기록 만료 시 보관·병합 상태와 미커밋 변경 유무를 확인한 뒤 관리 대상만 정리한다.

| G4   | 반영 승인·복구, 자동 위임·예약·스킬 연결                 | 두 탭 동시 승인, 검증 뒤 대상 이동, ref 변경 직후 서버 강제 종료, 위임 만료에서 중복 반영 0건. 다른 마스터도 같은 대상 큐를 사용하며 원본의 사용자 변경을 보존한다. |

첫 파일럿은 로컬 저장소 하나에서 실시한다. A는 실행 목록, B는 결과 문서 화면의 개선을 맡는다. 두 변경을 합친 앱에서 **실행 목록 → 결과 열기 → 목록 복귀**를 조작하고, 통합 후보의 SHA와 화면 증거를 연결한다. 병렬화의 효율은 같은 규모의 직렬 실행과 비교해 개발 시작부터 통합 검사 통과까지 걸린 시간, 통합 대기, 재작업 횟수로 평가한다.

### 이번에 실험한 Git 동작

일회용 로컬 저장소에서 실제 worktree와 브랜치를 만들었다. 같은 파일 상단과 하단의 변경은 한 후보에 합쳐졌다. 같은 줄의 서로 다른 변경은 충돌했고 병합을 취소하자 직전 후보 SHA로 돌아왔다. 함수명을 바꾼 가지와 이전 함수명을 사용하는 가지는 Git 병합에 성공했지만 합친 코드의 실행 검사는 실패했다. 이미 움직인 별도 대상 ref에 예전 SHA를 조건으로 갱신하자 Git이 거절했다. 원래 브랜치와 미추적 파일은 보존됐다. 이 결과는 Git 설계의 기술 실증이며 G0–G4의 Workplot 제품 인수 검사는 앞으로 수행한다.

## G2 구현 및 검증 · 2026-11-23

라이브러리와 와이어 편집기의 **개발 작업 실행**에서 확인한 커밋이 출발점이다. Workplot이 로컬로 관리하는 Git 저장소에 작업 ID마다 브랜치와 worktree를 하나씩 만든다. 같은 소스의 개발 작업은 동시에 두 개까지 실행할 수 있다. 마스터 실행도 등록된 Git 대상을 받으면 두 자식에게 각각 독립된 작업 공간을 준다. 실행 상세의 **작업 및 AI 호출 기록**에 원본 폴더, 독립 작업 폴더, 브랜치, 현재 커밋이 표시된다.

단계 속성의 **Git 작업 폴더 권한**에서 읽기 또는 수정을 선택한다. 기본값은 화면 구현 노드나 단일 작업 노드에 수정을 허용한다. 읽기 노드는 읽기 전용 Codex 샌드박스를 사용한다. 성공한 수정은 서비스 하위 경로를 검사한 후 해당 작업 브랜치의 커밋으로 남긴다. 원본의 미커밋 자료는 원본에 보존된다. 업무 실행과 원본 브랜치 병합은 별개이며 병합은 G3에서 다룬다.

## G3 통합 큐

Git 대상을 지정한 마스터의 두 개발 작업이 완료되면 자식의 커밋을 마스터 와이어 순서로 큐에 넣는다. 이전에 완료한 Git 마스터는 **Git 통합 큐에 추가**로 접수할 수 있다. 같은 체크아웃과 대상 브랜치를 사용하는 마스터들은 마지막으로 검사를 통과한 후보부터 이어간다. 마스터 상세의 **Git 통합 큐**에서 작업별 소스·병합 기준·후보 커밋, 변경 파일, 충돌 파일 또는 검사 출력을 볼 수 있다.

Git의 3방향 병합이 성공하면 별도 worktree에서 후보를 검사한다. 현재 검사기는 macOS에서 저장소 루트의 npm 프로젝트를 지원한다. 기준 커밋에 `test`가 필요하고, 정의된 `typecheck`, `build`, `test:e2e`도 실행한다. 잠금 파일과 로컬 npm 캐시로 의존성을 재현한다. 격리 환경에서 준비 또는 검사가 실패하면 그 작업을 검증 실패로 남긴다.

통과한 커밋은 Workplot 관리 저장소의 `refs/workplot/verified/<실행 ID>/<후보 SHA>`로 보존한다. 같은 줄 충돌이나 통합 테스트 실패 후에도 다음 작업은 마지막 통과 후보에서 시작한다. 원본 브랜치에 반영하는 승인은 G4 범위다.

재현은 `npm run build` 후 `node qa/git-integration.mjs`로 한다. 같은 파일의 두 구간 병합과 추가·삭제·이름 변경, 같은 줄의 충돌, 개별 테스트 통과 후 병합된 API 계약 테스트 실패를 실제 Codex와 Chromium으로 확인한다. [실행·파일·검사 기록](../.local/git-validation/g3/git-integration.json)
