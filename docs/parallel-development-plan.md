# 병렬 개발 마스터 워크플롯

2026-11-22 작성. 세션 인계와 복구부터 구현 중.

## 사용자가 경험할 흐름

사용자는 목표와 합격 기준을 입력하고 과제, 의존 관계, 재사용할 하위 워크플롯이 담긴 와이어를 확인한다. 실행을 누르면 독립 과제 최대 두 개가 같은 기준 소스에서 출발한다. 마스터 화면에서 각 과제의 상태와 결과를 열고 실패한 가지만 재시도할 수 있다. 검증한 변경을 차례로 통합한 후, 합쳐진 작업본의 결과와 로컬 앱 반영 여부를 확인한다.

## 구현 순서

| 단계                  | 개발 내용                                                                                                                                                                                | 다음 단계로 넘어가는 기준                                                                                                                                                                                |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. 실행 계약과 기준선 | 마스터 정의에 과제 ID, 선행 과제, 하위 흐름 ID·버전, 입력·출력, 과제별 합격 기준을 저장한다. 시작 시 작업 중 변경을 포함한 소스 기준선을 고정한다. 기존 직렬 흐름은 기존 경로로 읽는다.  | 순환·없는 참조는 실행 전에 차단한다. 편집·저장만으로 자식 실행은 0건이다. 시작 후 하위 정의를 수정해도 실행 버전은 유지된다.                                                                             |
| 2. 독립 실행과 복구   | SQLite에 부모·자식 실행과 시도를 기록한다. 동일 부모·과제·시도의 접수를 원자적으로 처리하고 실행 ID별로 프로세스, 승인, 중단을 관리한다. 첫 버전의 개발 슬롯은 2개다.                    | 두 탭의 중복 시작에도 각 자식이 한 번 생성된다. 두 Codex PID의 활동 구간이 겹친다. 한 가지 실패·재시도 중 다른 가지의 산출물 해시가 유지된다. 서버 재시작과 한도 대기 뒤에는 기존 체크포인트를 조회한다. |
| 3. 작업본과 통합      | 자식마다 독립 작업본·결과 폴더·QA 데이터를 배정한다. 공통 계약이 필요한 과제는 선행 노드로 올린다. 통합 슬롯은 1개로 두고, 첫 변경 반영 뒤 두 번째 변경을 최신 통합본에서 다시 검사한다. | 같은 파일을 건드린 두 변경을 자동 덮어쓰지 않는다. 충돌한 과제만 조정할 수 있고, 최종 빌드·회귀 검사 실패 시 로컬 앱 반영이 일어나지 않는다.                                                             |
| 4. 마스터 화면        | 기존 와이어에 분기·합류와 실행 상태를 표시한다. 자식 노드를 누르면 지침·로그·변경·QA 근거가 열리고 같은 마스터로 돌아온다. 가지 중단과 전체 중단을 구별한다.                             | 실제 브라우저 390px·1440px에서 실패한 가지 찾기 → 해당 가지만 재시도 → 통합 결과 열기를 검증한다. 새로고침과 두 탭에서 동일한 서버 상태를 표시한다.                                                      |
| 5. 실제 개발 파일럿   | A는 실행 단계에서 편집 위치 찾기, B는 비교 대상 실행 다시 찾기로 시작한다. 과거 실패 로그로 재현 조건을 먼저 확인하고 각 묶음에서 대표 사용자 동작 하나를 선택한다.                      | 실제 로컬 Codex로 분기·실패·재시도·합류를 끝내고 두 동작을 합친 앱에서 확인한다. 기존 직렬 실행·승인·중단·부분 재실행 QA도 통과한다.                                                                     |

## 세션 인계와 복구

각 가지는 원래 목표, 기준 소스와 흐름 버전, 완료 결과와 검증 근거, 시도한 접근과 확인된 실패 이유, 남은 범위와 재개 위치를 다음 세션에 전달한다. 실패 원인을 관찰하지 못한 경우에는 미확인으로 기록한다. 다음 세션은 기존 산출물 해시를 확인하고 자기 가지에서 미완료인 단계부터 시작한다.

첫 구현은 기존 실행 경로의 재시도 체크포인트에 실패 안내를 보관하고 고정된 워크플로 버전, 단계 ID, 확인한 문서명·해시와 함께 새 호출에 전달한다. 과거 체크포인트에 실패 이유가 없으면 미확인으로 둔다. 전체 소스 기준선과 가지별 개발 판단 기록은 마스터 실행 계약에서 추가한다.

통합 인수 검사에서는 A 실패·B 완료 시점에 서버를 재시작한다. A만 다시 실행하고 B의 호출 수와 산출물 해시를 전후 대조한다. 두 탭에서 A의 재시도를 동시에 접수해도 후속 시도는 한 번만 생성되어야 한다.

## 운영 판단

마스터가 작업을 나눌 때는 변경 파일뿐 아니라 공통 데이터 계약, 테스트 데이터와 포트, 선행 산출물을 확인한다. 승인 대기나 한도 대기는 CPU 작업 슬롯을 점유하지 않도록 하고 기존 사용자 승인과 위임 만료 규칙을 따른다. 전체 중단은 신규 접수를 닫고 활성 자식 종료 여부를 기록한다. 통합이 막혀 검증 완료 작업본이 쌓이면 신규 개발 접수를 늦춘다.

첫 릴리스 평가는 같은 기준 소스와 과제 두 개로 직렬·병렬 실행의 시작부터 통합 QA 통과까지 걸린 시간, 재작업 횟수, 통합 대기 시간을 기록한다. 이번 파일럿에서 기능 효과와 처리시간을 따로 판정하고 이후 슬롯 수를 결정한다.

## 두 자식 실행 이정표 · 2026-11-22

로컬 서버에서 저장한 마스터 계획에 독립 과제 두 개가 있을 때 각각의 고정 버전으로 실행한다. 같은 마스터 실행 ID로 두 탭이 시작해도 같은 두 자식 ID를 반환한다. 과제별 승인·로그·결과는 기존 실행 상세에서 조회한다. 시작은 로컬 세션의 `PUT /api/master-plans/{planId}/runs/{runId}`, 조회는 `GET /api/master-runs/{runId}`를 사용한다. 자식은 저장된 워크플로의 기본 입력을 사용한다. 이 이정표의 실행기는 추가 선행 과제나 다음 세션 자동 시작을 포함한 구성을 접수 전에 거절한다.

격리 QA 재현 명령은 빌드 후 `node qa/master-parallel.mjs`다. 두 실제 Codex PID의 동시 생존, 중복 시작, A 실패·B 완료, 서버 재시작, A 단독 재시도와 B의 파일 해시 보존을 검사한다. 병렬 개발 소스 작업본의 통합과 마스터 화면은 후속 단계다.

## 화면 작업본의 격리와 통합 · 2026-11-22

두 독립 과제 중 화면 개발 도구를 사용하는 과제가 있으면 실행 접수 시 웹 앱의 `src` 파일 내용을 SQLite에 함께 보존한다. 각 가지의 첫 화면 작업은 이 기준선을 복제하고 같은 가지의 후속 화면 작업은 직전 작업본의 해시를 확인해 이어간다. 문서 전용 마스터는 화면 소스를 복제하지 않는다.

두 가지가 모두 완료되면 서버가 계획에 적힌 순서대로 변경을 합친다. 같은 파일의 서로 다른 변경은 파일 단위 충돌로 기록한다. 변경이 생긴 단계마다 TypeScript, Vite 빌드, Chromium 화면 검사를 실행한다. 실패한 가지, 마지막 통과 작업본, 검사 근거는 실행 데이터 디렉터리에 남는다. 통과한 산출물은 격리된 통합 후보 앱이다. 운영 소스·배포 반영은 별도 단계다.

마스터 조회의 `integrating`과 `integration`에서 처리 중 여부와 최종 판정을 확인한다. 서버 시작 시 자식은 완료됐으나 통합 결과 기록이 없는 마스터를 다시 검사한다. 수동 재검사는 로컬 세션에서 `POST /api/master-runs/{id}/integration`으로 요청한다. 실제 생성부터 통합까지 재현하려면 빌드 후 `node qa/master-integration.mjs`를 실행한다.
