## 완료한 마일스톤 · 초안을 살려 두 번째 결과 만들기

기준 버전은 첫 커밋 `63009bc`다. 사용자가 말로 설계한 문서 업무를 한 번 마친 뒤, 마음에 드는 초안은 보존하고 검토 지침만 고쳐 새 수정본을 얻는 것을 목표로 한다.

1. **T05에서 실행 가능한 범위를 확인한다.** “매장 소개를 작성하고 Slack으로 발송해줘”처럼 현재 지원하지 않는 발송이 포함된 요청을 준다. 발송이 지원되지 않음을 안내하고 사용자가 “발송용 문서까지만 만들어줘”라고 선택한 뒤 설계안을 보여준다. 답변 전 신규 저장·업무 호출·발송은 각각 0건이어야 한다.
2. **T07에서 완료한 작업의 중간부터 다시 시작한다.** ‘초안 작성 → AI 검토 → 사용자 승인 → 수정본 작성’을 완료한 뒤, AI 검토 지침만 “주소와 영업시간을 원본 자료와 대조해줘”로 바꾼다. 사용자가 재실행을 선택하면 새 버전과 실행 ID를 기록하고 기존 초안을 검토 입력으로 전달한다.
3. **실제 Codex와 결과 파일로 판정한다.** 두 번째 실행에서 초안 작성은 0회, AI 검토는 1회다. 새 검토에 대한 사용자 승인 전 수정본 작성은 0회, 승인 후 1회여야 한다. 원래 실행 파일의 해시와 재사용한 초안의 해시를 대조하고, 대시보드에서 두 실행의 결과를 각각 다시 열 수 있어야 한다.

T09는 원안과 수정안의 실제 차이를 비교한다. 초보자가 도움 없이 설계부터 결과 비교까지 마치는지는 T10에서 관찰한다.

### T07 완료한 흐름에서 검토 지침 변경

대시보드에서 완료한 실행을 열고 **단계 지침을 바꿔 다시 실행**에서 작업을 선택한다. 저장된 흐름에 더 최근 버전이 있으면 해당 버전을 덮어쓰지 않도록 요청을 차단한다. 새 실행의 **이전 실행 보기**로 원래 문서를 다시 열 수 있다.

새로 완료하는 실행은 각 결과의 SHA-256을 보관하고 앞 단계의 파일을 재사용할 때 대조한다. 해시 기록을 도입하기 전에 완료한 실행은 이전 폴더에서 읽은 문서 내용을 새 실행의 시작점으로 사용한다.

실제 Codex는 새 실행에서 초안 호출 없이 주소와 영업시간을 대조했다. 새 승인 후 기존 초안과 새 검토문을 받아 수정본을 한 번 작성했다. 이전 실행의 세 문서와 로그는 SHA-256이 모두 같았다. 서버·계약 24건, 브라우저 4건, 실제 Codex 시나리오 31건이 통과했다. 완료한 실행에서 **문서 비교**를 열면 원안과 수정안, 두 문서에 공통으로 사용된 자료가 보인다. 기존 Codex CLI가 주소와 영업시간을 각각 대조하고 서버가 인용한 문자열을 원문에서 확인한다. 원본 근거가 누락되거나 충돌하면 두 문서 모두 확인 필요로 표시한다. 사용자가 체크한 부분만 원안에 적용한 문서를 SQLite에 별도로 저장하고 Markdown으로 내려받을 수 있다.

Q32는 주소만 반영해 기존 영업시간이 유지됐고, Q33은 영업시간만 ‘미기재’로 바꿨다. Q34는 두 공지의 충돌을 확인하고 주소만 바꿨다. 세 사례 모두 이전·새 실행의 원본 문서와 로그 해시를 보존했다. 전체 QA는 서버·계약 26건, 브라우저 4건, 실제 Codex 시나리오 34건을 통과했다. ### T10 첫 방문 관찰

2026-11-20에 기존 계정으로 로그인한 로컬 Codex와 Chromium을 사용했다. 참가자는 0명이다. 아래 시간은 빈 데이터베이스·새 브라우저에서 자동 조작한 1회 관측치다.

| 지점             | 개선 전 관측                                                                                                                  | 개선 후                                                                                                                             |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 목표 입력        | 대시보드 → 편집기 → 흐름 목록 → 목표 만들기로 세 번 눌러야 입력할 수 있었다.                                                  | 대시보드의 ‘목표로 시작’을 한 번 누른다.                                                                                            |
| 설계             | “매장 소개문을 만들어줘” 입력 후 시작 14.1초에 작성 노드 하나가 제안됐다. 이 설계로는 승인과 두 문서 비교를 진행할 수 없었다. | 사용자가 승인·비교 방식을 확인한 상태에서 같은 목표를 입력한다. 서버가 초안 → 사람 승인 → 초안을 전달받는 수정안의 연결을 검사한다. |
| 원본 자료와 실행 | 기존 설계 응답에는 매장 자료가 없었다.                                                                                        | 설계를 확인한 자리에서 실제 자료를 입력하거나 가상 자료를 선택한다. 저장 후 명시적으로 실행한다.                                    |
| 결과 비교        | 완료 화면의 비교 링크가 실행 상세 사이드바에 있었다.                                                                          | 결과 문서 상단에서 바로 비교를 연다.                                                                                                |

개선 후에는 목표만 타이핑하고 가상 자료를 선택했다. 대시보드 접속부터 선택 반영본 저장까지 32.6초였다. 설계 11.0초, 초안 6.5초, 승인 뒤 수정안 7.4초, 근거 대조 7.1초로, 요청 뒤 결과 표시까지의 합은 32.0초였다. 나머지 0.6초에는 자동 입력·클릭·검사가 포함된다. 재접속과 다운로드 검사는 종료 시각을 기록한 뒤 수행했다. 설계 응답부터 막혔던 개선 전에는 전체 완료 시간이 없다. [개선 전 기록](../.local/t10-before-pUwGxU/before.json) · [개선 후 단계별 시간](../.local/qa-acRHbV/Q35.json) · [내려받은 반영본](../.local/qa-acRHbV/first-use/선택한-반영본.md)

실사용자 관찰에는 처음 쓰는 참가자에게 목표 문구와 원하는 결과만 제공한다. 경로를 알려주지 않고 첫 클릭, 자료 선택, 승인, 비교, 저장 시각과 도움을 요청한 지점을 기록한다. 사람이 문서를 읽고 어떤 변경을 고를지 판단하는 시간은 자동 검사에서 측정할 수 없다.
